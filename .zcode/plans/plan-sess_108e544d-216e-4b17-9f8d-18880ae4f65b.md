## Full settings refactor

### Goal
Replace the current split-brain settings implementation with one standalone Settings screen that matches the supplied reference: app-level navigation, Back to workspace, grouped left navigation, Model settings as the primary screen, real provider/model data, and no editor tab or modal duplication.

### 1. Define one settings navigation model
- Add a typed `SettingsSection` union and a single source of truth in `workspaceStore`.
- Replace the misleading `openSettingsTab` implementation with `openSettingsScreen(section?)`; keep a temporary compatibility wrapper only where needed, then migrate all active callers.
- Remove unused `isSettingsModalOpen`, `isCustomizationsModalOpen`, and their context exports.
- Track `settingsReturnMode` so Back returns to the exact prior Agent/Editor surface.
- Synchronize `settingsActiveSection` with the screen so command-palette and toolbar links open the requested section instead of always showing Providers.

### 2. Make Settings a real app-level screen
- Update `App.tsx` so Settings replaces the workspace viewport, not just the editor content, while preserving Agent/Editor mounts behind it.
- Add a dedicated Settings shell/header inside the settings screen with the reference’s window-like spacing and a clear Back to workspace action.
- Hide workspace-only `TitleBar`/`StatusBar` controls while Settings is active, or introduce a settings-specific header so the screen is visually independent rather than an editor tab.
- Remove the `EditorTab.type === 'settings'` route and all code that creates/renders a settings editor tab.
- Rename `ForgeSettingsTab` to `SettingsScreen` and move it out of the editor component namespace.

### 3. Decompose the monolith into maintainable settings components
Create a settings feature folder with prop-driven components:

- `SettingsScreen`: screen layout, section selection, keyboard focus/scroll handling.
- `SettingsHeader`: Back, title, workspace context.
- `SettingsSidebar`: search, grouped navigation, active state, responsive collapse.
- `SettingsSectionHeader`, `SettingsRow`, `SettingsField`, `SettingsToggle`, `SettingsEmptyState` shared primitives.
- `ModelSettings`: active model, configured providers, model search, provider/model controls.
- `ProviderList`, `ProviderRow`, `ProviderForm`, `ModelRow`, `ModelForm`.
- `GeneralSettings`, `McpSettings`, `SkillsSettings`, `AgentsSettings`, `RulesSettings`, `PrivacySettings`, `ShortcutsSettings`.

Use semantic CSS variables/design tokens rather than repeating editor-specific color literals. Keep the reference’s light/dark neutral palette, restrained borders, compact rows, and flat list treatment; do not use nested card stacks as the page structure.

### 4. Make settings data real and consistent
- Consolidate provider/model reads and writes onto one authoritative path. Prefer the existing Wails provider APIs and normalize persistence keys to `forge_ade_*`; stop writing legacy `my_ade_*` keys.
- Ensure add/edit/delete/fetch/select provider/model actions have loading, success, error, and empty states.
- Use the store’s real `acpEnabled`/setter instead of a component-local shadow state.
- Use backend agent definitions for the Agents section; remove hardcoded frontend agent catalog entries except an explicitly marked empty/loading state.
- Use real MCP list/save/delete/reconnect/discovery APIs; remove local-only fake mutations and show connection errors/statuses.
- Treat Skills as discovered/imported backend skills; remove local-only fake CRUD unless a real backend write API is added.
- Remove the empty fake Rules list and either render real persisted definition rules or show an honest “No rules configured” state with the actual configuration path.
- Make privacy toggles consistently persisted and visibly labeled as local settings until backend enforcement exists; never imply telemetry is active when it is not.
- Remove sample providers/models, hardcoded default model labels, old My-ADE copy, and fabricated branch/workspace values.

### 5. Migrate every settings entry point
- Update `TitleBar`, `StatusBar`, `ActivityBar`, `CommandPaletteModal`, `AgentHomeView`, `AgentInputBar`, and any active sidebar entry to call the canonical screen action with valid section IDs.
- Remove “subagents” and stale `~/.my-ade/rules` command entries unless matching real sections exist.
- Ensure Settings launches with the requested section (Privacy, Agents, Models, etc.) and Back works from every entry point.
- Remove or archive the orphaned `global-settings-modal.tsx` implementation after migrating any genuinely useful backend-backed actions into the new sections.

### 6. Accessibility and responsive behavior
- Add `nav`/`main` landmarks, a single screen heading, `aria-current` for the active section, keyboard-focusable navigation, and visible focus rings.
- Use labeled inputs and semantic switches/radios for provider fields, model selection, toggles, and destructive controls.
- Add disabled/loading/error states and `aria-live` feedback for model fetching and saves.
- Make the sidebar collapse into a compact section picker on narrow windows; allow provider headers/model rows to wrap without overflow.

### 7. Verification
- Run a repository import-graph audit to confirm only one settings screen remains reachable and no settings editor tab/modal is active.
- Run frontend TypeScript/build checks and Go tests.
- Run the Impeccable mechanical detector on the new settings screen.
- Manually verify each entry point, requested-section navigation, Back-to-workspace behavior, provider/model CRUD, empty states, dark/light themes, and responsive layout.
